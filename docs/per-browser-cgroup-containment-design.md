# Per-browser cgroup containment — jdz feasibility and review contract

**State: design only / BLOCKED for implementation and live launch.** Checked read-only on the web-ai-showcase VM on 2026-10-09. Paul authorized a *per-browser cgroup-scoped* hard cleanup via the hub; this does **not** authorize host configuration changes, a Chrome launch, a global/numeric-PID/process-group kill, a foreign-scope kill, or `--disable-crashpad-for-testing`. The outstanding `0t0`, `tw3`, `jxd`, `crn` and `4ti` browser gates stay blocked until the isolation and independent failsafe are reviewed and driven under an explicit exclusive slot. In particular, no 63-second whole-browser SIGKILL case is asserted solved here.

## 1. Read-only VM evidence

- `cat /proc/self/cgroup` (observed via read-only command) → `0::/system.slice/fleet-sdk-host.service`.
- `systemctl show fleet-sdk-host.service`: `User=exedev`, `ControlGroup=/system.slice/fleet-sdk-host.service`, `Delegate=no`, `DelegateSubgroup=` empty, unit `/etc/systemd/system/fleet-sdk-host.service`, no drop-ins, `KillMode=process`. The service unit currently contains no `Delegate=` property.
- `/sys/fs/cgroup` is writable cgroup2; the host service has `cpuset cpu io memory pids` available in `cgroup.controllers`, empty `cgroup.subtree_control`, but its `cgroup.procs` and `cgroup.subtree_control` are `0644 root:root` and `cgroup.kill` is `0200 root:root`. The lane cannot safely create or tear down a child subtree there. `/sys/fs/cgroup/cgroup.procs`, `/sys/fs/cgroup/system.slice/cgroup.procs` and `/sys/fs/cgroup/user.slice/cgroup.procs` are `0644 root:root`.
- `user@1000.service` is active and delegated (`Delegate=yes`, controllers `cpu memory pids`); `app.slice/cgroup.kill` is writable by `exedev`. This **does not prove a safe per-browser scope**: the earlier `jxd` Chrome moved its own PID from a capped user service to sibling `app-com.google.Chrome-*.scope` through user-bus `StartTransientUnit`, before navigation. This is a directly observed escape. This lane has neither `XDG_RUNTIME_DIR` nor `DBUS_SESSION_BUS_ADDRESS` in its environment (an explicit user-bus socket address works for read-only `systemctl --user show`). Do not use a user `.scope` as an escape-proof boundary just because it is creatable.
- systemd is v255.4; `/proc/self/status` reports `Seccomp: 2`, one filter, so availability of `clone3(CLONE_INTO_CGROUP)` is **unknown** without a separately authorized kernel syscall capability check. No child cgroup or test process was created here.

Kernel semantics relevant to review: [cgroup v2 delegation](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#delegation) requires write permission at the common ancestor's `cgroup.procs` to migrate across subtrees as an unprivileged caller; [cgroup.kill](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#cgroup-kill) sends SIGKILL recursively, protects against concurrent forks/migrations and cannot be used for threaded cgroups. See [systemd cgroup delegation](https://systemd.io/CGROUP_DELEGATION/) for `Delegate=` and single-writer ownership. The root-owned common ancestors **suggest** user-manager migration out of a delegated `/system.slice` subtree will fail; prove it with a reviewed, bounded test rather than assuming it for Chrome.

## 2. Required owner-operated root change (proposed, NOT applied)

Only the VM owner/root operator can schedule a coordinated drop-in and restart for the actual host service. Candidate `/etc/systemd/system/fleet-sdk-host.service.d/20-browser-delegation.conf`:

```ini
[Service]
Delegate=cpu memory pids
DelegateSubgroup=supervisor
```

`DelegateSubgroup=supervisor` is proposed to put the SDK host/lane processes in a leaf while the delegated service parent is kept free for controller distribution. This is an ops proposal, **not a command to execute from a project lane**; restarting `fleet-sdk-host.service` terminates/restarts the current Pi lane and must be scheduled by hub ops. Before implementation, independently verify the setting is supported on this systemd build and that it does not change host reaper/accounting policy. After owner rollout, read-only recheck: `Delegate` lists the requested controllers; the service parent and its `cgroup.procs`/`cgroup.subtree_control` are writable by `exedev`; main lane lies in `supervisor`; `cpu memory pids` are available/appropriately enabled; the kernel exposes a writable `cgroup.kill` on a **unique disposable owned child** (creating that child itself is a separately authorized fixture, not part of this read-only phase). Refuse before launching Chrome if any assertion fails.

## 3. Isolation plan for independent review — not implementation permission

1. The launch controller must remain **outside** the child cgroup. Hold an open fd for the expected delegated service root; verify filesystem type, path, ownership and inode. Generate a cryptographically unpredictable per-launch name with `O_EXCL`/`mkdir` semantics; never reuse a name, search by profile marker, infer ownership from a PID, or target a sibling. The only target is that pinned child fd. A systemd-managed system scope instead of a direct delegated child is an alternative **only** with a separately specified privileged creation/lease protocol; a user-manager transient `.scope` is not an acceptable fallback.
2. Place Chrome into the child **before Chrome's `execve`** using an independently audited race-free mechanism: `clone3(CLONE_INTO_CGROUP)` with a pinned cgroup fd, **or** a small launcher that starts outside the child, writes `0` to the child's `cgroup.procs` to move **itself** there, verifies its own membership and only then calls `execve(chrome)`. A pre-exec failure must abort without executing Chrome; the helper's placement path must be independently reviewed. If both mechanisms are unavailable, refuse the launch—never quietly fall back to a post-exec numeric PID migration, a plain Chrome spawn, or a user `.scope`. Bind the controller to the launch token, fd and actual cgroup membership. Forks, setsid and detached handlers must inherit the child unless a privileged migrator explicitly moves them; verify the observed Chrome/handler paths under an exclusive no-model gate. Before exec set finite child `memory.max` and `pids.max` limits, plus `memory.oom.group=1`, and verify readback; ops must choose concrete values after reserving headroom for the controller/guardian within the fleet's separate 3 GB total job-tree cap. A limit sized only from downloaded weights or fixed equal to 3 GB is not safe. Hitting any bound is a failed diagnostic, not an automatic model retry.
3. Controller-scope teardown must target **only that pinned child fd** after filesystem/path/inode/parent ownership checks, write exactly `1` to its `cgroup.kill` once, and then bound-wait (proposed initial deadline: 5 s, subject to fixture review) for `cgroup.events` `populated 0` and no live members in the subtree. `cgroup.procs` at the top alone does not count grandchildren. Inventory **all** members before the write, including unexpected renderer/zygote/handler children; an unexpected *process name* inside the verified, exclusively owned child is **not** grounds to skip its scoped teardown. Refuse on cgroup boundary/fd identity mismatch; if a process independently proven to belong to a foreign launch was moved **inside** the child, ownership is broken: preserve evidence, abort acceptance and escalate to the owner because no automatic action can guarantee both cleanup and no collateral kill. Never use `pkill`, negative PGID, numeric-PID `SIGKILL`, `systemctl stop` on a sibling, or an unreviewed broader ancestor. Disclose that exact-child `cgroup.kill` is SIGKILL. On a timeout or D-state residual, report members and remain BLOCKED; do not broaden the target or infer success. Per [kernel cgroup v2 docs](https://docs.kernel.org/admin-guide/cgroup-v2.html), zombies do **not** appear in `cgroup.procs` and exit can clear `populated` before reaping; a parent still must reap its direct child separately for process hygiene, not as a prerequisite for `populated 0`.
4. Close DevTools before teardown. Remove the launch's profile only **after** `populated 0`, so live Chrome cannot recreate it. Every failure/timeout/retry/normal close follows the same scoped teardown path; no retry may spawn a second child before the first is proved empty. `scripts/browser.mjs` currently has two spawn abort paths (`DevToolsActivePort` absent, CDP connect failure), four launch attempts, signal/exit hooks and fire-and-forget callers; all must be handled. A Node `process.on('exit')` hook may only perform a synchronous exact-child write; it cannot await the zero-members check, which belongs to the separately supervised controller/deadline owner. Any test gate that runs long uses the existing bounded fleet queue and an independent owner to account for process-tree/VM memory policy.
5. **Unresolved external failsafe:** if the Node controller itself is SIGKILLed, its exit hook cannot write `cgroup.kill`. A deadline/lease owner outside the controller's killable tree must have an independently reviewed, exact-child cleanup capability. A direct delegated child alone does not solve controller death; neither this document nor a successful normal-close A/B test may claim it does. The precise lease owner, deadline, fd/path handoff, and reaping/accounting contract are mandatory before any live Chrome grant. `KillMode=process` on the current SDK host is not an automatic child-group cleanup guarantee.

No disabled-by-default switch may silently restore the preexisting `scripts/browser.mjs` negative-PGID Chrome teardown path for this safety gate. For a scope-required probe, lack of any capability is a **pre-spawn hard error**, not a degraded mode. Keep already-running unrelated validators out of a partial integration until their ownership/lifecycle is specified.

## 4. Review and experimental gates (future, separate authorization)

- **Independent design review first:** challenge delegated-root permissions, scope identity/fd confinement, pre-exec placement, user-bus migration, controller-death failsafe, no-internal-process controller rule, `cgroup.kill` threading semantics, and every abort path. If any guarantee is not available, remain BLOCKED and return an exact ops prerequisite.
- **After owner config and separate fixture grant:** disposable non-Chrome A/B scopes under a 3 GB process-tree cap plus foreign sentinel in a distinct scope; set/read back reviewed finite `memory.max` and `pids.max` and `memory.oom.group=1` before spawn, then test OOM and PID-limit failure cleanup separately. Prove child A empty after its one scoped kill (including unexpected *internal* child names), B and sentinel alive **and in their original cgroups**, refusal on boundary/identity mismatch, parent/controller exit deadline behavior, path reuse refusal, and clean scope removal. Capture service/cgroup logs and exact unit/path identities. A fixture is not a Chrome proof.
- **Only then**, request an exclusive, bounded **no-model Chrome** slot and a pre-reviewed cleanup failsafe. Verify membership at initial spawn, after Chrome's user-bus scope attempt, after normal close and after TERM; inventory **all** descendants (handlers and non-handlers). After a refused user-bus migration, prove Chrome still exposes CDP and can navigate/interact with an inert local fixture—`EPERM` alone is not functional success. Require zero surviving members, no migration, B/sentinel survival, and cleanup even on diagnostic failure. Any migration, unreadable identity, timeout, or residual means FAIL/BLOCKED; never count it as acceptance.
- `jxd` W8 q8 inference, `crn` decision-model browser inference and `4ti` demos require their own later grants, runtime/memory measurement and route-specific acceptance. A successful scope-only fixture cannot supply model latency, browser usability or a `built` claim.
