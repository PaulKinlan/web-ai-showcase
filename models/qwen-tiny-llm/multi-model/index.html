use case · multi-model · Silero VAD + Whisper + Qwen2.5

Voice agent: speak, and it calls a tool

Three on-device models in one real-time loop. Silero VAD listens to the mic and works out when you stopped talking, Whisper transcribes that utterance, and Qwen2.5-0.5B-Instruct decides which of six tools to call and with what arguments. The tool really runs — the timer really counts down, the note is really saved — and the model gets the result back to answer in a sentence. No server, no API key, nothing uploaded.

Unverified — not yet published

This route is not linked from the catalogue yet. Its three stages are wired to real models and the page is honest about every state, but the full chain — Silero VAD endpointing, Whisper transcription and a genuine Qwen2.5 tool call — has not yet been run end to end on a device with WebGPU and a microphone. Until that pass is recorded, treat anything you see here as unproven. Nothing is faked: if a stage fails, it will say so.

        Why this matters

        Voice assistants have always been a round trip: your audio goes to someone's server, a big model decides what you meant, and an answer comes back. Every part of that loop just ran on the visitor's device, in a tab, for about 600 MB of one-time download — and the interesting half isn't the transcription, it's the function call. A model that can pick a tool and fill in its arguments is a model you can wire to your app's actions.

        • Hands-free UI for anything. Point the tool schemas at the actions your app already exposes and users can drive it by voice — in a workshop, a kitchen, a warehouse, a car park.
        • Voice input where audio must not leave. Clinical notes, legal dictation, HR conversations: the recording never becomes someone else's log line.
        • Zero marginal cost. No per-minute ASR bill and no per-token LLM bill, so a feature that would be too expensive to leave running can just stay on.
        • Works offline. Once cached, the whole loop runs on a plane, in a basement, on a flaky site connection.

        How the tool call actually works

        There's no special "function calling API" — it's the chat template. Pass tools to apply_chat_template and Qwen2.5 writes the schemas into the system turn itself, then replies with a <tool_call> block you parse, run, and hand back as a tool message: 

        import { pipeline } from "@huggingface/transformers";

const qwen = await pipeline("text-generation", "onnx-community/Qwen2.5-0.5B-Instruct",
  { device: "webgpu", dtype: "q4f16" });

const tools = [{ type: "function", function: {
  name: "get_time",
  description: "Get the current date and time, optionally in another city's time zone.",
  parameters: { type: "object", properties: { timezone: { type: "string" } }, required: [] },
}}];

const messages = [
  { role: "system", content: "You are a voice assistant running in the browser." },
  { role: "user",   content: transcriptFromWhisper },
];

// The template serialises `tools` into a <tools> block and documents the reply format.
const prompt = qwen.tokenizer.apply_chat_template(messages, {
  tools, add_generation_prompt: true, tokenize: false,
});
const [{ generated_text }] = await qwen(prompt, { max_new_tokens: 160, do_sample: false });

// generated_text → <tool_call>{"name":"get_time","arguments":{"timezone":"Asia/Tokyo"}}</tool_call>
const call = parseToolCalls(generated_text)[0];
const result = runTool(call);            // your code, your app's real action

// Second pass: the same messages plus the assistant's call and the tool's result.
messages.push({ role: "assistant", tool_calls: [{ type: "function", function: call }] });
messages.push({ role: "tool", content: JSON.stringify(result) });

        Greedy decoding (do_sample: false) matters here: sampling makes a 0.5B model far more likely to mangle the JSON. Everything else is the ordinary text-generation pipeline.
