Practical: index a long document, then store 6× smaller vectors

While EmbeddingGemma 1 stopped at 2048 tokens (verified across config, tokenizer, and model card), EmbeddingGemma 2's model card documents an 8K context window (8192 tokens, 1024-token sliding window) while its ONNX export config.json specifies text_config.max_position_embeddings 262144 and text_config.sliding_window 512. Chunking a long document into semantic windows keeps each passage focused while staying safely within supported bounds. Once indexed, the Matryoshka dial lets you truncate stored vectors from 768 down to 128 dimensions—a 6× reduction in storage footprint (from 3,072 bytes to 512 bytes per chunk)—re-ranking instantly from in-memory vectors without re-embedding.

768 → 512 → 256 → 128. Truncates and re-normalizes cached 768-d unit vectors in memory with zero re-embedding.

Everything runs on-device via WebGPU: the document text never leaves your browser, the embeddings live in memory as Float32 arrays, and moving the slider slices the vector dimensions and re-normalizes Euclidean length via matryoshka(). At 128 dimensions, storing each vector in IndexedDB or OPFS takes only 512 bytes (versus 3,072 bytes at 768-d)—a 6× savings for constrained mobile devices.
